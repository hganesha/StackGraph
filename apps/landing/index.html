Software estate intelligence

The code is writing itself.Nobody is drawing the map.

Coding agents dropped the cost of producing software. The cost of understanding what got produced did not move. StackGraph reads the estate back from source and keeps a live model of what you run, why it exists, what it depends on, where it runs, and what is worth changing.

At 11:40 on a Tuesday night, an agent working on a payments service needed to debounce a form handler. It reached for the utility library it had seen most often, added the dependency, and moved on. The pull request was four lines long. The tests passed. A reviewer approved it the next morning without opening the lockfile.

Every party behaved reasonably. The agent solved the problem it was given. The reviewer read the diff it was shown. And the estate changed shape without anyone recording that it had.

Now multiply that by the number of agents currently committing to your repositories, running at a cadence no architecture review board was designed to sample.

The enterprise problem is no longer that organizations have vulnerabilities. It is that they can no longer answer plain questions about their own software: what exists, what business function it serves, what it is built from, where it runs, whether the technology is still a sound bet, and what should change.

The cost of producing software is falling faster than the cost of understanding it.

StackGraph product thesis, §2.1

01 / Sensor

Connect read-only and start at the repository

A read-only connection to your repository host is the first sensor. StackGraph reads languages and their proportions, build systems, monorepo boundaries, service boundaries, ownership metadata, manifests, lockfiles, and infrastructure files. A repository is where the reading starts. It is not the answer.

02 / Technology

Separate what is listed from what is used

Scanners parse package.json, pyproject.toml, lockfiles, tsconfig, framework configuration, and the imports themselves. A package sitting in a manifest and a package referenced in production code are recorded as different facts, because they lead to different decisions.

03 / Dependencies

Resolve the graph so a finding can be explained

Direct, transitive, dev, peer, and optional edges are resolved with the registry origin, the integrity hash, and the lockfile behavior that produced them. When something is wrong three hops down, the path from your application to it is printable.

04 / Deployment

Read the intended runtime out of the repository

Dockerfiles, Compose, Kubernetes, Helm, Terraform, CloudFormation, Pulumi, and CI pipelines are normalized into compute type, environment, and provider. Declared intent now, observed runtime later, with the drift between them reported rather than averaged away.

05 / Business

Attach the technology to something worth money

Applications map upward to capability, process, function, and value chain stage, from curated business maps, service catalogs, imported architecture data, and inference that carries its own confidence. This is the layer that turns a finding into a decision somebody owns.

Chapter two · Evidence

A manifest is a claim, not an inventory.

A package listed in package.json means somebody once wanted it there. It says nothing about whether the code still calls it, how much of it is reached, or what job it is doing. Most tooling collapses that distinction and then reports a number nobody can defend in a review.

StackGraph refuses to collapse it. Every fact carries the class of evidence that produced it, and that class stays attached wherever the fact travels.

Raw observation and StackGraph's reading of it are stored apart. FACT: last release 4.2 years ago is a different record from ASSESSMENT: maintenance health LOW. An architect can argue with the second without anyone re-litigating the first, which is the only way this kind of conclusion survives contact with the team that owns the code.

No material conclusion without evidence. A number on a screen that cannot open into the file, line, registry response, advisory, or curated record behind it does not belong on the screen.

Chapter three · Judgment

Ask what the code needs done.

An engine that matches package to package will answer the lodash question with another utility library. That is the wrong question. Three functions are in use, and once you know which three, the decision space opens up.

Candidates are drawn from your own organizational standards, the implementations already running inside your estate, the public ecosystem, and the runtime you are already paying for. They are scored on capability fit, runtime compatibility, internal adoption, maintenance health, migration surface, and dependency complexity. Sometimes the best replacement for a dependency is no dependency.

And the answer never arrives as a single line. Counter-signals ship next to the recommendation, because retry semantics do differ, integration tests will be required, and a recommendation that hides its own weak points does not survive an architecture review.

Chapter four · Repetition

Four teams already built the same thing.

Package-level cleanup is the small prize. The larger one is organizational: the same capability implemented independently across an estate, each version maintained by people who do not know the others exist.

Candidates come from structural fingerprints, dependency and symbol usage, embeddings over the implementations themselves, and covering tests where they exist. Similarity is offered as a candidate for review and never as proof of equivalence, because the fourth implementation usually exists for a reason somebody in the building still remembers.

Counted across the estate, the same signal produces a measure of technology entropy: how much variation exists per capability, which teams are introducing it, and whether it is growing. Variation is not automatically waste. It just has to be visible before anyone can argue about it.

Chapter five · The outside world

The ecosystem already ran the experiment.

Millions of public repositories record which technologies were adopted, which were abandoned, what replaced them, and roughly what the swap cost. StackGraph maintains a reference graph around the technologies your estate actually contains rather than crawling everything, then keeps release recency, release cadence, maintainer activity and concentration, archive state, license, runtime compatibility, adoption trend, and co-occurrence against each one.

The most useful part of it is the migration graph. Watch a public repository where one technology leaves and another arrives while the behavior around it stays put. Aggregate thousands of those and a migration stops being folklore.

That pattern is reusable in both directions. It tells an architect what the change will cost, and it gives a coding agent the context to perform the change correctly once a human has approved it.

Installed base is a poor guide to trajectory. A technology can hold an enormous footprint while almost no new system chooses it. StackGraph tracks new-project selection, upgrade velocity, migration-in rate, and migration-out rate separately, so a large estate does not get mistaken for a healthy one.

Chapter six · Viability

A package can be secure and still be a bad bet.

Vulnerability management asks one question and answers it well. It has nothing to say about a dependency with no known CVEs, no maintainer, no release since 2022, and no compatibility story for the runtime you are moving to. That package passes every scanner in the building.

01 / The finding

Most tooling stops at the package

A scanner returns a critical advisory against a transitive dependency three hops down. It is correct, it is unranked, and it arrives alongside four hundred others. Nobody can tell from this alone whether it matters this quarter.

02 / The code

Walk it up to something that runs

The resolved graph names the repository that pulled it in and the service built from that repository, with the deployment evidence showing it reaches two production environments and one public entry point.

03 / The business

Give it a name the board recognizes

The business map carries this service into the Billing Platform, and the Billing Platform into a capability rated criticality 5 with a named owner. The advisory becomes potential exposure in customer invoicing.

04 / The general case

The same walk runs for everything else

An unsupported runtime, an abandoned package, an unmaintained base image, a single-region deployment, an on-prem dependency under a cloud-exit program. Each one propagates along the identical path, which is what makes a mixed list of technical findings rankable against each other.

Chapter seven · Allocation

Where the next ten million goes.

Findings without ranking are a backlog, and backlogs get funded last. Modernization is an allocation problem: business importance weighed against the viability gap and the opportunity, discounted by confidence, divided by what the migration will actually cost.

A recommendation is a proposal, not an instruction. Each one carries its review state, and StackGraph tracks the lag between a decision being accepted and anything landing in a repository. Accepted work sitting untouched past thirty days is itself a reportable finding.

Chapter eight · Absence

An empty result is not a clean bill of health.

Every scanner in this category enumerates things that exist. Ask one what your estate is missing and it returns nothing, which the reader takes as reassurance when it usually means unobserved. Those last two states are the ones that matter. A cell marked not applicable was ruled out on purpose in a versioned tenant profile, with a record of who ruled it out. A cell marked not evaluable means StackGraph is telling you it cannot see, which is a different sentence from telling you there is nothing there.

The same honesty runs at estate level. An assurance score reports what share of the estate the platform can actually reason over, scored separately for scan freshness, analyzable ecosystems, evidence completeness, connector health, and repository availability, so a gap is attributed to the thing that caused it instead of being smoothed into an average.

Set a governed target profile beside the observed canvas and the difference between the architecture you approved and the architecture you have becomes a diff, versioned and auditable, rather than a slide somebody maintains by hand.
